# Octa-Core : Distributed AI Workflow Orchestrator

## Idea
This project originates from the simple idea, rather than you as a user giving an llm feedback to improve its output, why not let another llm do it for you.

## Problem Statement
LLMs on their own are highly unreliable due to hallucinations and in usecases which require the LLM to generate code, this can lead to faulty code or code with a lot of holes which the user has to fix on their own.

This project aims to fix that by bringing together different LLMs as evaluators with their own instructions to evaluate the output given by the base model.
By leveraging the strengths of different families of LLMs a user can specifically configure various LLMs to evaluate a certain aspect of the output and give their verdict.

## High-Level Architecture
<img width="1404" height="1203" alt="Valve Architecture 2" src="https://github.com/user-attachments/assets/b1c46600-1353-4224-8923-42a811f88f41" />


- A user first configures the Base Model responsible for generating the output to the user.
- Then they configure the Judges (either singular or a panel of judges) with their own instructions.
- Upon starting the workflow, the Base Model generates an output which the judge panel evaluates.
- Each of the Judges gives a verdict `is_valid:` `True` or `False`.
- If a `False` verdict is returned, the Judge provides targeted critique (e.g., "Line 23 violates instruction X").
- If Valve Consensus is not reached the feedback along with the original prompts and output is given back to the base model as `chat_history`. This is called as one retry.
- If the Valve Consensus is reached, the valve is opened and the output is given to the user.

## Valve Consensus Criteria
The Valve opens if one of the following criteria are met:

**1. Consensus is Met (Success)**

$$\frac{\sum_{i=1}^{N} w_i v_i}{\sum_{i=1}^{N} w_i} \ge acceptability$$

Where $w_i$ is the weight of the $i^{\text{th}}$ judge model and $v_i$ is the value of the verdict of the model (the value of `is_valid`). 0 for False, 1 for True.
The weights for each judge model can be custom configured by the user and the acceptability defaults to 0.75 but can be changed by the user.

**2. Max Retries Reached (Termination)**

$$
Retries > Max Retries
$$

The value of Max Retries defaults to 5, but can be changed by the user.

## Core Architecture and State Management
The project uses Temporal to guarantee durable execution and robust state management across the orchestration lifecycle. The retryable and non retryable types of errors are specified according to the error codes generated by each API in `activities.py`.
The multi-model Judge Panel executes asynchronously and hence the total time for a judge panel consensus is defined by the maximum time taken by any of the APIs in the judge panel to return an output. The feedback for each retry is fed in the form of chat history to the base model example for gemini the chat history after one retry is fed as 
```
chat_history = [
                {"role":"user","parts":[{"text":'base model prompt'}],
                {"role":"model","parts":[{"text":'first response'}]},
                {"role":"user","parts":[{"text": consolidated_feedback}]}}
                ]
```

Note: Only the feedback of models that reject the output (`is_valid` is False) is given back to the base model.

## Tech Stack
This project uses the following tech stack:
- Orchestration: Temporal (Durable execution, event-sourced state tracking)
- Concurrency: Python 3.11+ (asyncio)
- Data Validation: Pydantic (Strict type safety and enforcing structured LLM outputs for judge output , is_valid and feedback)
- Inference: Direct API integration (Google Gemini, OpenAI, Anthropic, Ollama)

## Scope and Limitations
System Scope
- Durable State Management: The system is explicitly scoped to guarantee fault-tolerant, long-running orchestration of multi-model LLM calls using Temporal workflows.
- Strict Schema Enforcement: Out-of-the-box data integrity is strictly bounded by Pydantic validation schemas to ensure deterministic structured outputs before consensus logic triggers.
  
Limitations
- The project was designed to run with a local server, hence you will find instances where some of the variables are hard coded such as "localhost:7233" in `worker.py`
- A weaker model such as qwen 3.5:9b running locally sometimes will not adhere to the strict pydantic output when acting as a judge and this might cause the activity to retry multiple times which causes increase in execution time.

## Quick start guide
1. Initialize a .env file with the api keys of the models you wish to use in the following manner:
   ```
   GEMINI_API_KEY=your_gemini_key
   ANTHROPIC_API_KEY= your_anthropic_key
   OPENAI_API_KEY=your_openai_key
   ```
   For ollama, ensure the model you wish to use is setup and installed.
3. Install all dependencies.
4. Initialize the judges and base model along with values of acceptability and max_retries in `starter.py` 
5. Initialize a temporal server with the code:
   ```
   temporal server start-dev 
   ```
6. Initialize a worker in a new terminal with the code
   ```
   python worker.py
   ```
7. Run `starter.py` with the code
   ```
   python starter.py
   ```
